\section{Boundedness Analysis}\label{sec:boundedness}

This section presents the actual boundedness analysis, that uses
the results of a preliminary side-effect analysis (Sec.~\ref{sec:side_effect}).

\emph{Paths} are leftvalues
(Def.~\ref{def:exp_com}) that start from a variable and dereference \<final> fields only,
so that their value cannot be affected by side-effect.
%
\begin{definition}[Paths]\label{def:path}
  The set $\paths\subseteq\LValue$ of \emph{paths} is the minimal set \st
  \begin{itemize}
  \item if $v\in\Var$ then $v\in\paths$ is rooted at $v$ and its type is the declaration type of $v$;
  \item if $\pi\in\paths$ is rooted at $v$ and
    has type $C$ and if $C.f$ is a \<final> field of type $t$ defined in class $C$,
    then $\pi.f\in\paths$ is rooted at $v$ and has type $t$.
  \end{itemize}
\end{definition}
%
\begin{example}
  At line~\ref{ponzi1:require} in Fig.~\ref{fig:ponzi1},
  \<this> is a path rooted at \<this> of type \<Ponzi1>,
  \<amount> is a path rooted at \<amount> of type \<int> and
  \<this.investors> is a path rooted at \<this> of type \<List<Contract\texttt{>}>.
\end{example}
%
The list bound to a path $\pi$ cannot be replaced by side-effect,
but it can be enlarged by side-effect. When that does not happens,
$\pi$ \emph{survives} the side-effect.
%
\begin{definition}[Path Survival]\label{def:survival}
  Given $\pi\in\paths$ and a set of types $U$, then $\pi$ is said to
  \emph{survive any enlargement of a list of a type in $U$} (or just
  \emph{$\pi$ survives $U$}) if
  \begin{itemize}
  \item $\pi$'s type is not a list, or
  \item $\pi$'s type is \<List<$t'$\texttt{>}> and $t'$ has no shared subtype with any $t''\in U$.
  \end{itemize}
\end{definition}

\begin{example}
  In Fig.~\ref{fig:ponzi1}, the path \<this.investors> has type \<List<Contract\texttt{>}>
  and hence it does not survive $\{\<Contract>\}$ (just take $t'=t''=\<Contract>$
  in Def.~\ref{def:survival}).
  The path \<amount> has type \<int>, hence it survives $\{\<Contract>\}$.
  In Fig.~\ref{fig:lottery1}, at line~\ref{lottery1:expand}, the path
  \<this.rounds> has type \<List<Round\texttt{>}> hence it survives
  $\{\<TicketBatchSale>\}$, since \<Contract> and \<TicketBatchSale> have no
  shared subtype. But \<List<Round\texttt{>}> does not survive $\{\<Object>\}$ nor
  $\{\<TicketBatchSale>,\<Object>\}$: just take $t'=\<Round>$ and $t''=\<Object>$
  and observe that \<Contract> is subtype of \<Object>.
\end{example}

\begin{definition}[Boundedness States]\label{def:bo}
  A \emph{boundedness state} \|bo| is either $\bot$ or a finite
  collection of constraints
  \[
  \left\{\left.\begin{array}{c}
  \size{\pi_1}\le n_1\\[-0.7ex]
  \ldots\\
  \size{\pi_k}\le n_k
  \end{array}\right|\pi_i\in\paths\text{ and }n_i\in\nat\text{ for every $i=1,\ldots,k$}\right\}.
  \]
  The set of all possible boundedness states is $\bo$.
\end{definition}
%
The intuition is that $\bot$ represents the empty set of concrete states and
that \|bo| represents the set of all concrete states
where $\pi_i$ holds a list whose length is at most $n_i$, for every $i=1,\ldots,k$.
%
\begin{proposition}[Abstract Domain]\label{prop:abstract_domain}
  In terms of abstract interpretation, any $\|bo|\in\bo$ is an abstraction
  of concrete states and $\bo$ is an abstract domain whose bottom is $\bot$
  and whose other elements are ordered as $\|bo|_1\sqsubseteq\|bo|_2$
  if and only if for every $(\size{\pi}\le n_2)\in\|bo|_2$ there exists
  $(\size{\pi}\le n_1)\in\|bo|_1$ with $n_1\le n_2$.
  Therefore, $\varnothing$ is the top (least precise) element of $\bo$.
  The least upper bound operator yields the other operand if any operand is
  $\bot$, otherwise it is
  \[
  \|bo|_1\sqcup\|bo|_2=\left\{\size{\pi}\le\max(n_1,n_2)\left|\begin{array}{l}
  (\size{\pi}\le n_1)\in\|bo|_1\\
  (\size{\pi}\le n_2)\in\|bo|_2
  \end{array}\right.\right\}.
  \]
\end{proposition}
%
An assignment can invalidate some bounds, but only if $\pi$
is a single variable, since paths only refer to \<final> fields,
whose value cannot be changed.
%
\begin{definition}[Bounds Invalidation]\label{def:invalidation}
  Given $\|bo|\in\bo$ and $\pi\in\paths$, the \emph{invalidation of $\pi$ in $\|bo|$}
  is $\bot$ if $\|bo|$ is $\bot$, otherwise it is
  \[
  \|bo|^{-\pi}=\begin{cases}
  \{(\size{\pi'}\le n)\in\|bo|\mid\pi'\text{ is not rooted at }v\} & \text{if $\pi$ is a variable $v$}\\
  \|bo| & \text{otherwise.}
  \end{cases}
  \]
\end{definition}
%
A comparison operation between two expressions can improve a boundedness state,
when it carries information about the size of a path.
Similarly, an assignment can sometimes improve a boundedness state.
%
\begin{definition}[Bounds Improvement and Assignment]\label{def:improvement}
  Given $\|bo|\in\bo$, the
  \emph{improvement of \|bo| \wrt a comparison expression $\cop{\exp_1}{\exp_2}$}
  is $\bot$ if $\|bo|$ is $\bot$, otherwise it is
  \begin{align*}
    \|improve|(\|bo|,\copfull{\size{\pi}}{\le}{n})&=\|bo|\cup\{\size{\pi}\le n\}\\
    \|improve|(\|bo|,\copfull{\size{\pi}}{<}{n})&=\|bo|\cup\{\size{\pi}\le n-1\}\\
    \|improve|(\|bo|,\copfull{\size{\pi}}{==}{n})&=\|bo|\cup\{\size{\pi}\le n\}\\
    \|improve|(\|bo|,\copfull{n}{\ge}{\size{\pi}})&=\|bo|\cup\{\size{\pi}\le n\}\\
    \|improve|(\|bo|,\copfull{n}{>}{\size{\pi}})&=\|bo|\cup\{\size{\pi}\le n-1\}\\
    \|improve|(\|bo|,\copfull{n}{==}{\size{\pi}})&=\|bo|\cup\{\size{\pi}\le n\}\\
    \|improve|(\|bo|,\cop{\exp_1}{\exp_2})&=\|bo|\text{ in all other cases.}
  \end{align*}
  The \emph{assignment in \|bo|} is (here, $\pi,\pi'\in\paths$):
  \begin{align*}
    \|assign|(\|bo|,\assign{\pi}{\new{\mathtt{List}}{}})&=\|bo|^{-\pi}\cup\{\size{\pi}\le 0\}\\
    \|assign|(\|bo|,\assign{\pi}{\pi'})&=\|bo|^{-\pi}\cup\{\size{\pi}\le n\mid(\size{\pi'}\le n)\in\|bo|\}\\
    \|assign|(\|bo|,\assign{\pi}{\exp})&=\|bo|^{-\pi}\text{ in all other cases not considered above}\\
    \|assign|(\|bo|,\assign{\lvalue}{\exp})&=\|bo|\text{ if $\lvalue\not\in\paths$.}
  \end{align*}
\end{definition}

Boundedness is a property of states hence we present
its analysis in operational form, as a derivation rule over boundedness states
(Def.~\ref{def:bo}):
$\pair{p}{\|bo|}\boderivation\pair{p'}{\|bo|'}$ means that
the execution of the command at program point $p$ from a boundedness state \|bo| performs a single
step and then continues with the execution of the command at program point $p'$
from a boundedness state $\|bo|'$.
%

  $\left(\Exp\times\bo\right)\boderivation\bo$
  that derives the approximation of the post-states
  from the approximation of the pre-states.
  The boundedness derivation rule $\boderivation$ for commands
  in Fig.~\ref{fig:bo_derivations_commands} is a small step semantics
  $\left(\PP\times\bo\right)\boderivation(\PP\times\bo)$.

%
In Fig.~\ref{fig:bo_derivations_expressions}, the
rule for constructor call first evaluates
the actual parameters, recursively, then projects the result on the bounds
that are not affected by the side-effects of the constructor. This
rule is intraprocedural, since it does not enter the body of the constructor
but simply embeds its side-effects in the result.
In Fig.~\ref{fig:bo_derivations_commands}, the rule for method call
works similarly, but considers the
union of the side-effects of all targets of the call. The rule for assignment
updates the boundness aproximation with the effects of the assignment
(Def.~\ref{def:improvement}). The rule for \<push> is the most interesting one.
It evaluates receiver and parameter of \<push> and then splits the
resulting bounds into those about lists whose static type guarantees that
they cannot be enlarged by the \<push> ($\|bo|_{\mathit{survives}}$)
and those for lists that might be enlarged instead
($\|bo|_{\neg\mathit{survives}}$). The approximation of the size
of the former remains valid, while that of the latter is conservatively
weakened by one (one element might be added to those lists).
The rule for \<removeFirst> cannot improve the constraints, instead,
since it is not enough to know that a list might be affected to conclude
that it will be affected and that the approximation of its size can be
safely decreased by one. Therefore, that rule leaves the constraints unchanged,
conservatively.
The rule for \<require> tries to improve
(Def.~\ref{def:improvement}) the boundedness state
with information entailed by the required condition, that must hold or
else the computation stops. The
same for the conditional, that non-deterministically proceeds
to the \emph{then} branch if the condition holds and to the \emph{else} branch
if its opposite holds. The rules for $\for{v}{\exp}{\com}$
non-deterministically enter the inner loop after evaluating $\exp$, or re-enter the
loop without re-evaluation $\exp$ or, finally, exit the loop. That
considers more execution paths than the concrete semantics
of that command, which is fine since the abstract semantics must consider
an over-approximation of all execution paths.

The rules in Fig.~\ref{fig:bo_derivations_commands} have been given
as a small step semantics in order to allow the computation of a
boundedness state at each program point, through a
fixpoint that saturates all execution paths. Namely, the analysis records a boundedness
state at each program point through a map $\beta$. Initially,
$\beta(p)=\bot$ at every $p$.
For each method with body $\com$ at program point $p_{\|start|}$, the analysis starts from $\pair{p_{\|start|}}{\varnothing}$
($\varnothing$ is a worst-case assumption at the beginning
of the method: nothing is known there about the size of the lists)
and computes all possible derivations from there.
Whenever a configuration $\pair{p}{\|bo|}$ is reached, the analysis updates
$\beta$ as $\beta(p):=\beta(b)\sqcup\|bo|$.
If $\beta(p)$ changed, the derivation continues
from $\beta(p)$ itself. Otherwise, it stops. At the end,
$\beta$ is the boundedness analysis.
Formally, this means that the derivation rules in Fig.~\ref{fig:bo_derivations_commands}
work on configurations $\langle p,\|bo|,\beta\rangle$ rather than $\langle p,\|bo|\rangle$,
all update $\beta(p)$ and all check that this update actually modifies $\beta(p)$, or otherwise
the rules are stuck. We do not formalize this here, for simplicity.

The computation of the boundedness analysis $\beta$ can consider the methods in any order,
being intraprocedural. However, we require to proceed by following, backwards, the strongly-connected
components of the methods \wrt the calling relation (who calls whom). This allows to improve
the approximation of the calls to constructors with
a limited form of interprocedural analysis, by
propagating the approximation at the end of the constructors into the caller, upon renaming. Namely, the
$\|assign|$ function from Def.~\ref{def:improvement} considers a further case now:
%
\[
\|assign|(\|bo|,\assign{\pi}{\new{\mathtt{C}}{\ldots}})=\|bo|^{-\pi}\cup\{\size{\pi}\le n\mid\size{\<this>}\le n\in\beta(r)\}
\]
if the assignment and the constructor of \<C> are in distinct components and $r$ is the program
point of the \<return> instruction of the constructor. This occurs, for instance, at
line~\ref{lottery1:call_to_round} in Fig.~\ref{fig:lottery1}.

In Ex.~\ref{ex:boundedness_computation}, the computation of the boundedness analysis
converges. This is expected for simple code such as smart contracts. However,
$\bo$ has infinite ascending chains hence that computation
might diverge, in general, and a widening operator is needed, to force
termination after a given number $\kappa$ of iterations~\cite{CousotC77}.
%
\begin{definition}[Widening Operator]\label{def:widening}
  The \emph{widening operator on $\bo$} is set intersection:
  $\nabla(\|bo|_1,\|bo|_2)=\|bo|_1\cap\|bo|_2$.
\end{definition}
%
By using a widening, when reaching a program point $p$ with an approximation $\|bo|$,
the analysis $\beta$ is updated as
\[
\beta(p):=\begin{cases}
\beta(p)\sqcup\|bo| & \text{for the first $\kappa$ iterations}\\
(\beta(p)\sqcup\|bo|)\nabla\beta(p) & \text{from the $(\kappa+1)$th iteration.}\\
\end{cases}
\]
%
\begin{proposition}[Termination]\label{prop:termination}
  The operator $\nabla$ is a widening operator on $\bo$.
  Therefore, the computation
  of a boundedness state at each program point must terminate in
  a finite number of iterations.
\end{proposition}

In the following, we assume that a boundedness analysis has been computed.
This information is used to warn about boundedness bugs.
%
\begin{definition}[Bounded Lists]\label{def:bounded_lists}
  All lists of type $t$ are \emph{bounded} in a program
  if for every $\push{\exp_1}{\exp_2}$ in the program such that
  $\<List<$t'$\texttt{>}>$ is the type of $\exp_1$, 
  $t$ and $t'$ share a subtype and $p$ is the program point
  of the \<push> command,
  it is $\exp_1=\pi\in\paths$ and $(\size{\pi}\le n)\in\beta(p)$ for some $n\in\nat$.
\end{definition}
%
\begin{example}\label{ex:bounded_lists}
  Not all lists of $t=\<Contract>$ are bounded
  in \<Ponzi1> (Fig.~\ref{fig:ponzi1}), since the \<push>
  at line~\ref{ponzi1:expand} operates on $\<this.investors>$, of type
  $\<List<$t'$\texttt{>}>$ with $t'=\<Contract>$, $t$ and $t'$ share a subtype
  (\ieinitial \<Contract> itself), $\<this.investors>\in\paths$
  but the boundedness state computed at that \<push> is
  $\varnothing$ (Fig.~\ref{fig:boundedness_ponzi1}) and no
  $(\size{\mathtt{this.investors}}\le n)\in\varnothing$, for any $n\in\nat$.
  Instead, in \<Ponzi2> (Fig.~\ref{fig:ponzi2}), all lists of type $\<Contract>$
  are bounded since the boundedness state computed at the \<push>
  at line~\ref{ponzi2:creator} is $\{\size{\mathtt{this.investors}}\le 0\}$
  (Fig.~\ref{fig:boundedness_ponzi2})
  and that computed at the \<push> at line~\ref{ponzi2:expand} is
  $\{\size{\mathtt{this.investors}}\le 100\}$ (Fig.~\ref{fig:boundedness_ponzi2}).
  Similarly, in \<Lottery1> (Fig.~\ref{fig:lottery1}),
  not all lists of \<Round> and not all lists of \<TicketBatchSale> are bounded,
  since the boundedness state computed at the
  \<push> commands inside \<buy()> (Fig.~\ref{fig:lottery1}),
  that operate on such lists, is $\varnothing$ (Fig.~\ref{fig:boundedness_lottery1}).
  For the same reason, in \<Lottery2> (Fig.~\ref{fig:lottery2}),
  not all lists of \<Round> are bounded but all lists of \<TicketBatchSale>
  are bounded, since the only \<push> that operates on the latter
  is in \<buy()>, it works on $\<last.sale>\in\paths$ and
  the boundedness state there is $\{\size{\mathtt{last.sale}}\le 4999\}$
  (Fig.~\ref{fig:boundedness_lottery2}). 
\end{example}
%
\begin{definition}[Warning Generation]\label{def:warnings}
  Our boundedness analyzer issues a warning at each
  $\for{v}{\exp}{\com}$ command in the program, where
  $\exp$ has type $\<List<$t$\texttt{>}>$, if and only if it is not true that
  all lists of type $t$ are bounded (Def.~\ref{def:bounded_lists}).
\end{definition}
%
\begin{example}\label{ex:warnings}
  Our analyzer warns ar line~\ref{ponzi1:iteration} of
  \<Ponzi1> (Fig.~\ref{fig:ponzi1}), where a \<for> operates on
  \<this.investors> of type \<List<Contract\texttt{>}> but not all lists of
  \<Contract> are bounded in \<Ponzi1> (Ex.~\ref{ex:bounded_lists}).
  But it does not warn
  in \<Ponzi2> (Fig.~\ref{fig:ponzi2}), since all lists of \<Contract> are bounded there
  (Ex.~\ref{ex:bounded_lists}). It warns instead
  at line~\ref{lottery1:iteration} of \<Lottery1> (Fig.~\ref{fig:lottery1}),
  since the \<for> command there operates on \<this.round.sales> of type
  \<List<TicketBatchSale\texttt{>}> but not all lists of
  \<TicketBatchSale> are bounded in \<Lottery1> (Ex.~\ref{ex:bounded_lists}).
  It does not warn at that same \<for> command in \<Lottery2>
  (Fig.~\ref{fig:lottery2}), since all lists of \<TicketBatchSale> are bounded there
  (Ex.~\ref{ex:bounded_lists}). These results are exactly
  those foreseen in Sec.~\ref{sec:examples}.
\end{example}
%
Ex.~\ref{ex:warnings} shows that our analysis is correct and precise on the
examples from Sec.~\ref{sec:examples}. In general, however, boundedness is an undecidable
property, hence our analysis will be correct but imprecise. For instance, by replacing
the \<while> at line~\ref{ponzi2:require_limit} with an \<if>, the contract
\<Ponzi2> has still no boundedess issue, since the length of list \<investors> can
be $101$ at most at that line, hence a single \<removeFirst> is enough to bound its size
to $100$ at the subsequent \<push> at line~\ref{ponzi2:expand}. But our analysis fails
to identify that and issues a false alarm at the iteration at line~\ref{ponzi2:iteration}.
In this case, some form of class invariant is needed, which is beyond the scope
of our analysis.
