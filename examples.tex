\section{Examples of Boundness and Unboundedness}\label{sec:examples}

This section exemplifies the meaning and relevance of boundedness for
data collections in smart contracts. It provides concrete examples of smart
contracts, written in a pseudocode inspired by Solidity and Takamaka~\cite{OlivieriST25}
(the latter provides a clearer type system, inherited from Java). We prefer
to use pseudocode in order to concentrate on the semantics of the code rather than
on the idiosyncrasies of a specific programming language. Pseudocode allows us to
keep the syntax to a minimum.

\begin{figure}[t]
  \begin{lstlisting}[language=pseudo]
public class Ponzi1 extends Contract {
  private final List<Contract> investors = new List<>();|\label{ponzi1:investors}|
  private final static int MINIMUM_INVESTMENT = 1000;

  public Ponzi1() {
    investors.push(caller);|\label{ponzi1:creator}|
  }

  public payable void invest() {|\label{ponzi1:invest}|
    require(amount >= MINIMUM_INVESTMENT);|\label{ponzi1:require}|

    int eachInvestorGets = amount / investors.size();
    for investor in investors|\label{ponzi1:iteration}|
      investor.receive(eachInvestorGets);|\label{ponzi1:receive}|

    investors.push(caller);|\label{ponzi1:expand}|
  }
}
  \end{lstlisting}
  \caption{A smart contract that implements a Ponzi scheme. Investors get their money
    back, but only as long as new investors keep arriving after them. The list \<investors>
    is unbounded and, consequently, the loop at line~\ref{ponzi1:iteration} is unbounded as well.}
  \label{fig:ponzi1}
\end{figure}

Fig.~\ref{fig:ponzi1} shows a smart contract that implements a Ponzi scheme, inspired
by an example from~\cite{IyerD18}. It keeps a list of investors at
line~\ref{ponzi1:investors} where, as in Takamaka, \<Contract> is a superclass of both
contracts and externally-owned accounts, that are treated as a special case of contract.
That list gets initially populated for free by the constructor with
its caller (line~\ref{ponzi1:creator}, where \<caller> corresponds to
\<msg.sender> in Solidity). Subsequently, new contracts become investors
by calling the \<invest()> method and paying a minimal fee (\<amount> corresponds to
\<msg.value> in Solidity). This fee gets equally split among the existing investors
(lines~\ref{ponzi1:iteration} and~\ref{ponzi1:receive}) before the \<caller> is
added to the list of investors (line~\ref{ponzi1:expand}). There is no upper bound
to the size of the list \<investors> and there is no way of removing investors.
As long as users keep calling \<invest()>, the list
\<investors> can only grow arbitrarily long. Therefore, there is no upper bound
on the gas needed to execute the loop at line~\ref{ponzi1:iteration}. Namely,
once that gas cost
exceeds the maximum allowed for a blockchain transaction, the smart contract is
effectively blocked: method \<invest()> can only fail for gas exhaustion, reverting
all transaction updates, and some investors will never be able to cover their investment.
We will say that list \<investment> and the loop at line~\ref{ponzi1:iteration}
are \emph{unbounded} and we expect a sound boundedness analyzer to warn about an
unbouded loop at line~\ref{ponzi1:iteration}.

\begin{figure}[t]
  \begin{lstlisting}[language=pseudo]
public class Ponzi2 extends Contract {
  private final List<Contract> investors = new List<>();|\label{ponzi2:investors}|
  private final Map<Contract, int> balances = new Map<>();|\label{ponzi2:balances}|
  private final static int MINIMUM_INVESTMENT = 1000;

  public Ponzi2() {
    investors.push(caller);|\label{ponzi2:creator}|
  }

  public payable void invest() {|\label{ponzi2:invest}|
    require(amount >= MINIMUM_INVESTMENT);|\label{ponzi2:require}|

    int eachInvestorGets = amount / investors.size();
    for investor in investors|\label{ponzi2:iteration}|
      balances[investor] = (balances[investor] else 0) + eachInvestorGets;|\label{ponzi2:increase}|

    investors.push(caller);|\label{ponzi2:expand}|
  }

  public void withdraw() {
    int payout = balances[caller] else 0;
    balances[caller] = 0;|\label{ponzi2:noreentrancy}|
    caller.receive(payout);|\label{ponzi2:receive}|
  }
}
  \end{lstlisting}
  \caption{A smart contract that implements a Ponzi scheme, using the withdrawal pattern.
    The list \<investors>
    is still unbounded and, consequently, the loop at line~\ref{ponzi2:iteration} is unbounded as well.}
  \label{fig:ponzi2}
\end{figure}

Method \<receive()> at line~\ref{ponzi1:receive} of Fig.~\ref{fig:ponzi1} is the payment
method of class \<Contract>, that sends cryptocurrency to a contract.
Different programming languages
have different approaches to that method. For instance, Takamaka defines \<receive()>
as \<final> in class \<Contract>, so that its semantics cannot be redefined and
its call cannot lead to re-entrancy. Solidity, instead, allows its redefinition. It is
well-known that clever redefinitions of the payment method led to re-entrancy attacks
in Solidity contracts. Therefore, Solidity programmers require the paid contract
to take responsibility about the call to its own payment method, through the so-called
\emph{withdrawal pattern}. Fig.~\ref{fig:ponzi2} shows how the same smart contract
from Fig.~\ref{fig:ponzi1} would be written by a Solidity programmer. It uses an extra
map that keeps track of the \<balances> that each investor is still allowed to withdraw
(line~\ref{ponzi2:balances}). When new investors arrive, the balances of the previous
investors get increased at line~\ref{ponzi2:increase}, where \<balances[investor] else 0>
is the map value for \<investor> with $0$ as default if \<investor> does not belong to the map.
Solidity implicitly uses a default value for maps, but we prefer to make it explicit in our
pseudocode. When an investor wants to withdraw its balance, it calls method \<withdraw()>, taking
responsibility for any potential redefinition of its own \<receive()> method (line~\ref{ponzi2:receive},
where \<caller> is the same investor). The assignment
at line~\ref{ponzi2:noreentrancy} makes any potential re-entrancy harmless.
We want to make clear that this paper is not
about re-entrancy and that we are showing the contract in Fig.~\ref{fig:ponzi2} only to clarify
that unboundedness is not related to the potential re-entrancy bug in the contract in
Fig.~\ref{fig:ponzi1} since, in Fig.~\ref{fig:ponzi2},
list \<investors> and the loop at line~\ref{ponzi2:iteration}
are still unbounded and a sound boundedness analyzer should warn about it.

public class Ponzi3 extends Contract {
  private final List<Contract> investors = new List<>();|\label{ponzi3:investors}|
  private final static int MINIMUM_INVESTMENT = 1000;

  public Ponzi3() {
    investors.push(caller);|\label{ponzi3:creator}|
  }

  public payable void invest() {|\label{ponzi3:invest}|
    require(amount >= MINIMUM_INVESTMENT);|\label{ponzi3:require}|
    require(investors.size() < 100, "no more investors");|\label{ponzi3:require_limit}|

    int eachInvestorGets = amount / investors.size();
    for investor in investors|\label{ponzi3:iteration}|
      investor.receive(eachInvestorGets);|\label{ponzi3:receive}|

    investors.push(caller);|\label{ponzi3:expand}|
  }
}
  \end{lstlisting}
  \caption{A modified version of the smart contract in Fig.~\ref{fig:ponzi1}, that enforces
    an upper bound to the size of the list \<investors>, at line~\ref{ponzi3:require_limit}.
    The list \<investors>
    is bounded and, consequently, the loop at line~\ref{ponzi3:iteration} is bounded as well.}
  \label{fig:ponzi3}
\end{figure}

A solution to the unbounded list and loop in Fig.~\ref{fig:ponzi1} is simple: Fig.~\ref{fig:ponzi3}
shows a modified version of the smart contract from Fig.~\ref{fig:ponzi1} that just
adds a constraint on the size of \<investors> (line~\ref{ponzi3:require_limit}). This guarantees
that the size of that list is always $100$ at most and the iteration at line~\ref{ponzi3:iteration}
is bounded. We expect a sufficiently precise static
boundedness analyzer to issue no warning in the code in Fig.~\ref{fig:ponzi3}.
This example shows that the boundedness property is not related to the exact maximal gas cost of a loop:
$100$ iterations might be acceptable or not, depending on the specific maximal gas allowed
by each specific
blockchain for a transaction. Instead, boundedness is an abstract semantical and blockchain-agnostic
property about the definitely limited size of iterated containers.

public class Lottery1 extends Contract {
  public final static int TICKET_PRICE = 1000;|\label{lottery1:price}|
  private final List<Round> rounds; // all existing rounds|\label{lottery1:rounds}|
  private final long duration; // round duration|\label{lottery1:duration}|

  private static class TicketBatchSale {|\label{lottery1:sale}|
    private final Contract buyer;|\label{lottery1:buyer}|
    private final int tickets;

    private TicketBatchSale(Contract buyer, int tickets) {
      this.buyer = buyer;
      this.tickets = tickets;
    }
  }

  private static class Round { // ticket sale round|\label{lottery1:round}|
    private final long endTime;
    private final List<TicketBatchSale> sales;|\label{lottery1:sales}|
    private int totalTickets;|\label{lottery1:total_tickets}|
    private Contract winner;|\label{lottery1:winner}|

    private Round(long endTime) {
      this.endTime = endTime;
      sales = new List<>();
    }
  }

  public Lottery1(long duration) {
    this.duration = duration;
    rounds = new List<>();
    rounds.add(new Round(now + duration));|\label{lottery1:first_round}|
  }

  public payable void buy() {
    require(amount > 0 && amount % TICKET_PRICE == 0);|\label{lottery1:amount}|

    Round last = rounds.getLast();|\label{lottery1:last_start}|
    if (now > last.endTime) {
      last = new Round(now + duration);
      rounds.add(last);
    }|\label{lottery1:last_end}|

    int quantity = amount / TICKET_PRICE;
    last.sales.add(TicketBatchSale(caller, quantity));|\label{lottery1:add_sale}|
    last.totalTickets += quantity;
  }

  public void drawWinner(int roundNumber) {
    Round round = rounds[roundNumber];
    require(round.winner == NULL, "winner already drawn");|\label{lottery1:no_winner_yet}|
    require(now > round.endTime, "too early");|\label{lottery1:expired}|
    require(round.totalTickets > 0, "no tickets in round");|\label{lottery1:at_least_one_ticket}|

    int numWinningTicket = random(round.totalTickets);|\label{lottery1:random}|
    for sale in round.sales|\label{lottery1:iteration}|
      if (sale.tickets > numWinningTicket) {
        round.winner = sale.buyer;|\label{lottery1:set_winner}|
        round.winner.receive(TICKET_PRICE * round.totalTickets);|\label{lottery1:win}|
        return;|\label{lottery1:return}|
      }
      else
        numWinningTicket -= sale.tickets;
  }
}
  \end{lstlisting}
  \caption{A smart contract for a recurring lottery. Lottery rounds have a duration,
    after which a new round is created. Tickets are sold in batches. This contract
    suffers from an unbounded iteration at line~\ref{lottery1:iteration} on the unbounded
    list of sales in a round.}
  \label{fig:lottery1}
\end{figure}

Let us consider another example of smart contract, also inspired from an example
in~\cite{IyerD18}. Fig.~\ref{fig:lottery1} shows a smart contract for a recurrent lottery.
Each lottery ticket has a fixed price (line~\ref{lottery1:price}). Tickets are bought in batches
(inner class \<TicketBatchSale> at line~\ref{lottery1:sale}). The smart contract
keeps an unbounded list of rounds (line~\ref{lottery1:rounds}), each lasting
for \<duration> milliseconds (line~\ref{lottery1:duration}) and containing
the list of batch sales of tickets in the round (line~\ref{lottery1:sales})
and the total number of tickets sold in the round (line~\ref{lottery1:total_tickets}).
Each round eventually
gets a winner assigned (line~\ref{lottery1:winner}), which will be
one of the buyers of its batch sales
(line~\ref{lottery1:buyer}). The constructor assigns the duration of the rounds
and initializes the list of rounds to a list of one round, that expires after
\<duration> milliseconds from now (line~\ref{lottery1:first_round}).
Method \<buy()> is called by who wants to buy a batch of tickets.
It requires to pay an
\<amount> of cryptocurrency sufficient to buy exactly a batch of a
positive number of tickets (line~\ref{lottery1:amount}).
These tickets are bought for the last, most recent lottery round,
ensuring that a fresh new last round is added to the list of \<rounds> if its last
round was already expired (lines~\ref{lottery1:last_start}--\ref{lottery1:last_end}).
Method \<drawWinner()> draws the winner of a round, if this has not been drawn yet
(line~\ref{lottery1:no_winner_yet}), if the round has already expired
(line~\ref{lottery1:expired}) and if at least one ticket has been sold for that round
(line~\ref{lottery1:at_least_one_ticket}). If all such conditions hold, the number of
the winning ticket is randomly chosen between 0 (included) and the total number of
tickets in the round (excluded) (line~\ref{lottery1:random}).
Then the sales in the round are iterated (line~\ref{lottery1:iteration}), looking for the
buyer of the winning ticket, which gets assigned as the winner of the round
(line~\ref{lottery1:set_winner}) and receives all money collected from the ticket sales
in the round (line~\ref{lottery1:win}).

Method \<drawWinner()> is meant to be called by any actor, most likely by somebody
who bought some ticket in the round.
The iteration at line~\ref{lottery1:iteration} is unbounded, since there is
no upper bound to the number of sales allowed in a round (line~\ref{lottery1:add_sale}).
Therefore, the smart contract in Fig.~\ref{fig:lottery1}
suffers from an unboundedness bug and a sound static analyzer should warn
at line~\ref{lottery1:iteration} about that.
In practice, this means that there is a limit $X$
to the number of sales that that iteration can scan before running out of gas.
Therefore, a sale has a chance to win the round only if it is among the first $X$
sales of the round (thanks to the \<return> at line~\ref{lottery1:return}, that
exits the loop). Moreover,
an attacker might flood a new round with $X$ one-ticket sales and be sure to win
the round, by repeatingly calling \<drawWinner()> until a
$\<numWinningTicket>\le X$ is drawn. Other players could be unaware of the bug and
subsequently buy extra tickets without realizing that they have no chance to win and,
by buying tickets, they are
only increasing the jackpot that will be finally collected by the attacker.
Note that there is another unbounded container in Fig.~\ref{fig:lottery1}, that of the
\<rounds> (line~\ref{lottery1:rounds}). However, \<rounds> is not iterated in the code,
hence its unboundedness is not problematic and a static analyzer is expected to
issue no warning about \<rounds>, if it is precise enough.

\begin{figure}[t]
  \begin{lstlisting}[language=pseudo,numbers=none]
public class Lottery2 extends Contract {
  ...
  private final List<Round> rounds; // all existing rounds
  public final static int MAX_SALES = 5000;|\label{lottery2:max_sales}|
  ...
  public payable void buy() {
    require(amount > 0 && amount % TICKET_PRICE == 0);

    Round last = rounds.getLast();
    if (now > last.endTime) {
      last = new Round(now + duration);
      rounds.add(last);
    }

    if (last.sales.size() < MAX_SALES) {
      int quantity = amount / TICKET_PRICE;
      last.sales.add(TicketBatchSale(caller, quantity));
      last.totalTickets += quantity;
    }
  }
  ...
}
  \end{lstlisting}
  \caption{A modified version of the smart contract in Fig.~\ref{fig:lottery1},
    where the list of sales in a round is limited. Therefore, this version does not
    suffer from any unboundedness bug.}
  \label{fig:lottery2}
\end{figure}

A solution to the unboundedness bug in Fig.~\ref{fig:lottery1} is to
limit the maximal number of the sales in each round, as exemplified in
Fig.~\ref{fig:lottery2}. Note that the list \<rounds> remains unbounded in this new
version, since that is irrelevant. We expect a static boundedness analyzer to issue no
boundedness warning in Fig.~\ref{fig:lottery2}, if it is precise enough.
