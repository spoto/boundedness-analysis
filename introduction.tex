\section{Introduction}\label{sec:introduction}

Smart contracts are computer programs that run
in the nodes of a blockchain network. They code
an agreement among parties, that gets enforced by the properties of the underlying
blockchain. Namely, the blockchain's data immutability and its consensus
algorithm make it hard to violate the agreement, replace data or censure transactions.
This is desirable for protocols that must survive
in the wild, but it also means that software bugs, if present,
get enforced and cannot be patched.
Therefore, it is highly relevant to deploy correct smart contracts.
There is large literature on bugs that led to
protocol breaches and stolen money (for Ethereum,
see for instance~\cite{AntonopoulosW25}).
The well-known reentrancy issue shows that attacks to
smart contracts can actually be rather involved and exploit
misunderstood features of the programming language.
In general, Turing-complete programming languages
for smart contracts are useful but increase the risk
of bugs and losing money. The use of
new programming languages, sometimes with vague or misleading semantics,
complicates programming further.

A source of bugs in smart contracts is the completely different
style of interaction \wrt traditional software for desktop computers. Namely,
smart contracts run in the wild: after deployment, users (and attackers)
can call their API in any order and with any parameter.
In this sense, smart contracts look more like old-fashioned
servlets and general-purpose libraries than like software
for desktop computers. Their development requires careful analysis of their
API and extensive use of defensive programming, to foresee all
possible illegal uses. Not surprisingly, many developers,
often unexperienced juniors,
got overwhelmed by this complexity. Bugs thrived. Money got lost.

This paper focuses on a specific, frequent bug in smart contracts.
Namely, smart contracts often store data in containers, such as lists,
that can become arbitrarily large. This is fine as long as they do not get
iterated. Otherwise, the gas cost of the iteration might be arbitrarily large,
even larger than the maximum allowed for a single smart contract transaction.
If that happens, the iteration fails for gas exhaustion, which might block
some contract functionality and, in some case,
even lock money in the contract. This paper defines
a sound static analysis that infers, automatically,
a maximal size for iterated containers,
valid for all possible ways of calling the smart contract API.
We call such containers \emph{bounded} and the proposed verification technique
is consequently a \emph{boundedness analysis}.
Note that boundedness analysis does not compute the exact gas cost of each API function:
it just infers a bound for iterated containers.

Our boundedness analysis is an abstract interpretation of the
smart contract code into boundedness constraints that
allow one to infer if specific containers are definitely bounded and,
consequently, if their iteration is bounded. Otherwise, a warning is issued.
Abstract interpretation comes with a soundness guarantee: if no warning is generated,
then the code has no boundedness bug.

The contributions of this paper are:
%
\begin{enumerate}
\item a formal definition of the boundedness property for iterated containers;
\item a sound boundedness analysis, based on abstract interpretation;
\item a prototype implementation for a minimalistic smart contract language.
\end{enumerate}

The paper is consequently organized as follows.
Sec.~\ref{sec:examples} describes boundedness on
concrete examples of smart contracts, and the potential attacks allowed by unboundedness.
Sec.~\ref{sec:syntax} presents the syntax of a minimalistic language for smart contracts.
Sec.~\ref{sec:side_effect} defines the supporting side-effect analysis onthat language.
Sec.~\ref{sec:boundedness} defines the actual boundedness analysis.
Sec.~\ref{sec:implementation} reports preliminary results
with our prototype implementation.
Sec.~\ref{sec:discussion} discusses related work and concludes.
