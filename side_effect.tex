\section{Side-Effect Analysis}\label{sec:side_effect}

Given a command, it is useful to know
which already existing lists might be affected during its execution.
Previous work provides precise and complex static analyses for that
(see for instance aliasing and side-effect analysis in~\cite{SpotoMP10}).
Here, for simplicity, we present a simpler cheap side-effect analysis that,
nevertheless, is often precise enough on simple programs such as smart contracts.
Possible side-effects are an abstract interpretation of execution traces.
Therefore, our analysis is a bottom-up interprocedural
denotational semantics that uses an interpretation\ie inductive information about
the side-effects of the methods.
We do not discuss this further here, since it is standard technology
in semantics~\cite{Winskel93} and abstract interpretation~\cite{CousotC77}.
An example of computation is reported later.
%
\begin{definition}[Side-Effects Analysis]\label{def:side_effect}
  \begin{figure}[t]
    \begin{align*}
      \sideeffect{c}&=\sideeffect{v}=\sideeffect{\nop}=\varnothing\\
      \sideeffect{\new{C}{\exp_1,\ldots,\exp_n}}&=I(C.C)\cup\bigcup_{i=1}^n\sideeffect{\exp_i}\\
      \sideeffect{\push{\exp_1}{\exp_2}}&=\sideeffect{\exp_1}\cup\sideeffect{\exp_2}\cup
      \{t\mid\exp_1\text{ has type }\<List<>t\<\text{>}>\}\\
      \sideeffect{\call{\exp_0}{m}{\exp_1,\ldots,\exp_n}}&=\bigcup_{j=1}^k I(C_j.m)\cup\bigcup_{i=0}^n\sideeffect{\exp_i}\\
      \noalign{\centering\text{where $C_1.m\cdots C_k.m$ are the methods possibly called here}}
      \sideeffect{\ifetwo{\exp_1}{\exp_2}{\com_1}{\com_2}}&=\sideeffect{\exp_1}\cup\sideeffect{\exp_2}\cup\sideeffect{\com_1}\cup\sideeffect{\com_2}.
    \end{align*}
    \caption{The side-effect rules. They use an interpretation $I$ for the methods. The cases of expressions and commands
    not shown here are just a recursive descent on their syntax, as shown for the conditional command.}
    \label{fig:side_effect}
  \end{figure}
  %
  The set of element types of the already existing lists possibly modified during the
  execution of a command $\com$ is overapproximated by $\sideeffect{\com}$,
  defined in Fig.~\ref{fig:side_effect} by using an \emph{interpretation} $I$ that
  provides the possible side-effects of the methods.
\end{definition}
%
The origin of the side-effects are the \<push> commands (Fig.~\ref{fig:side_effect}),
that might side-effect all lists whose element type $t$ is that of their receiver.
Methods (and hence constructors) use the interpetation $I$ as an oracle
about the side-effects of their callee(s).
A method call, in object-oriented languages, may actually call a subset
$\{C_1.m\cdots C_k.m\}$ of the redefinitions of its static target method.
A sound overapproximation of $\{C_1.m\cdots C_k.m\}$
can always be easily inferred statically as the set of \emph{all} possible
redefinitions. More precise analyses exist~\cite{TipP00},
but they are probably overkill for smart contracts, that very rarely redefine methods.

The computation of the analysis
starts from an interpretation $I_0$ that yields $\varnothing$ as
side-effects of every method. The methods' bodies are then analyzed with the rules
in Fig.~\ref{fig:side_effect}, using $I=I_0$, to get an improved interpretation $I_1$.
This process is repeated to yield $I_2$ and so on, until a fixpoint $\intsideeffect$.
This will be reached after a finite number of iterations
since the rules in Fig.~\ref{fig:side_effect} are monotonic and the set of element types
of lists used in a program is finite.

\begin{example}\label{ex:side_effect}
  Fig.~\ref{fig:side_effect_examples} reports $\intsideeffect$ for the smart contracts from
  Sec.~\ref{sec:examples}\ie the element types of lists potentially modified during
  the execution of their methods.
  Consider Fig.~\ref{fig:side_effect_lottery1}, for instance.
  Its computation starts from an $I_0$ such that $I_0(M)=\varnothing$ for each $M$.
  Then $I_1(\<TicketBatchSale.TicketBatchSale>)=\sideeffect{\com}=\varnothing$,
  where $\com$ is that constructor's body
  (line~\ref{lottery1:constructor_tbs} in Fig.~\ref{fig:lottery1}) and
  by the rules in Fig.~\ref{fig:side_effect} (recursive descent, there is no \<push> inside
  $\com$). Similarly, $I_1(\<Round.Round>)=\varnothing$ as above and
  since $\sideeffect{\<new List()>}=I_0(\<List.List>)=\varnothing$ (rule for
  constructors in Fig.~\ref{fig:side_effect}).
  $I_1(\<Lottery1.Lottery1>)=\{\<Round>\}$ as above
  and since $\sideeffect{\<rounds.push(...)>}=\{\<Round>\}$ by the rule for \<push>
  in Fig.~\ref{fig:side_effect}. Similarly,
  $I_1(\<Lottery.buy>)=\{\<Round>,\<TicketBatchSale>\}$ and
  $I_1(\<Lottery.drawWinner>)=\varnothing$. The computation of $I_2$ leads to
  $I_2=I_1$, hence $I_1$ is the fixpoint in Fig.~\ref{fig:side_effect_examples}.
  %
  \begin{figure}[t]
    \begin{center}
    \begin{subfigure}{\textwidth}
      \begin{align*}
        \intsideeffect(\<Ponzi1.Ponzi1>)&=\{\<Contract>\}\\
        \intsideeffect(\<Ponzi1.invest>)&=\{\<Contract>\}
      \end{align*}
      \caption{The side-effect analysis of \<Ponzi1> in Fig.~\ref{fig:ponzi1}
      (that of \<Ponzi2> in Fig.~\ref{fig:ponzi2} is similar).}
    \end{subfigure}\\
    \begin{subfigure}{\textwidth}
      \begin{align*}
        \intsideeffect(\<TicketBatchSale.TicketBatchSale>)&=\varnothing\\
        \intsideeffect(\<Round.Round>)&=\varnothing\\
        \intsideeffect(\<Lottery1.Lottery1>)&=\{\<Round>\}\\
        \intsideeffect(\<Lottery1.buy>)&=\{\<Round,TicketBatchSale>\}\\
        \intsideeffect(\<Lottery1.drawWinner>)&=\varnothing
      \end{align*}
      \caption{The side-effect analysis of \<Lottery1> in Fig.~\ref{fig:lottery1}
        (that of \<Lottery2> in Fig.~\ref{fig:lottery2} is similar).}
      \label{fig:side_effect_lottery1}
    \end{subfigure}
    \end{center}
    \caption{The side-effect analysis of the smart contracts from Sec.~\ref{sec:examples}.}
    \label{fig:side_effect_examples}
  \end{figure}
\end{example}
%
The approximations in Fig.~\ref{fig:side_effect_examples} are correct
but sometimes imprecise. For instance, $\intsideeffect(\<Ponzi1.Ponzi1>)=\{\<Contract>\}$
is correct but could be improved as $\intsideeffect(\<Ponzi1.Ponzi1>)=\varnothing$,
since no existing list of \<Contract> is modified by that constructor:
the one at line~\ref{ponzi1:creator} of Fig.~\ref{fig:ponzi1}
is a fresh new list created at the previous line, not existing before the
execution of the constructor. More complex analyses can ovecome these imprecisions,
but the results in Fig.~\ref{fig:side_effect_examples} are good enough here.
